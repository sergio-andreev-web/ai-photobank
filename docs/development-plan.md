# AI Photobank MVP — план разработки по контрактам

## Как я понял продукт

Это закрытый корпоративный фотобанк. Администратор загружает фотографии пачками; приложение сохраняет оригинал, создает варианты изображения и обрабатывает его в фоновой очереди. Отдельный AI-сервис возвращает подпись, найденный текст, визуальные понятия и embedding. Laravel сопоставляет понятия с управляемым каталогом тегов. Существующие теги назначаются автоматически, а новые понятия попадают в очередь кандидатов и становятся тегами только после решения администратора. Пользователь ищет фотографии точными тегами, смысловым запросом или их комбинацией.

**Граница ответственности:** Nuxt ↔ публичный HTTP API Laravel ↔ HTTP API AI-сервиса. PostgreSQL и файловое хранилище принадлежат Laravel. AI-сервис не знает о тегах и БД. Загрузка не ждет выполнения AI.

Исходный документ сохранен без изменений в [technical-specification.md](technical-specification.md). Этот план — разбиение работ, а не замена ТЗ.

Общие правила для всех агентов лежат в [`.agents`](../.agents), а рекомендации по выбору модели — в [model-routing.md](model-routing.md).

Локальный диспетчер задач описан в [orchestrator/README.md](../orchestrator/README.md). Он назначает модель по типу задачи и запускает Codex/Claude в отдельных Git worktree после приемки зависимостей.

## Этапы и контрольные точки

| Этап | Результат | Что можно запускать параллельно |
| --- | --- | --- |
| 0. Основание | Git-репозиторий, структура monorepo, ответственные за файлы, правила интеграции | Подготовка среды и проработка контрактов |
| 1. Контракты | Проверенные OpenAPI/JSON Schema, enum и состояния, примеры, mock API, тестовые фикстуры, решения из списка ниже | Пока контракты утверждаются, команды готовят каркасы и инструменты |
| 2. Независимая реализация | Backend работает с FakeAiClient; frontend — с mock public API; AI — с mock моделями; инфраструктура запускает все сервисы | Backend, frontend, AI, инфраструктура в отдельных рабочих ветках |
| 3. Интеграция без GPU | Реальные HTTP-соединения Laravel ↔ mock AI и Nuxt ↔ Laravel, upload → очередь → теги/кандидаты → поиск | QA и исправления в границах владельцев модулей |
| 4. Реальные модели и качество | SigLIP2, затем Qwen3-VL; Mac MPS и RunPod CUDA; эталонные 300–500 фото, подбор порогов | AI и подготовка датасета/измерений |
| 5. Приемка MVP | Чистый запуск, тесты контрактов и E2E, сценарий из §75, проверка отказа AI и повторов, документация | Интеграция и исправления |

**Критический путь:** контракт → независимые модули → интеграция на mock AI → реальные модели → калибровка → приемка. Реальная GPU-модель не должна блокировать frontend и backend.

## Пакеты задач для агентов

Каждый файл ниже можно передать отдельному агенту вместе с исходным ТЗ. Одновременно работают владельцы разных каталогов.

| Пакет | Владеет | Вход | Независимый результат |
| --- | --- | --- | --- |
| [00 — Контракты](agent-tasks/00-contracts.md) | `contracts/**`, решения API | ТЗ | OpenAPI, схемы, примеры, моки |
| [01 — Backend](agent-tasks/01-backend.md) | `apps/api/**` | зафиксированные контракты | Laravel API и фоновые процессы с FakeAiClient |
| [02 — Admin frontend](agent-tasks/02-admin-frontend.md) | `apps/admin/**` | public OpenAPI | Nuxt, работающий с mock API |
| [03 — AI service](agent-tasks/03-ai-service.md) | `services/ai/**` | AI OpenAPI и JSON Schema | FastAPI с mock моделями, затем SigLIP2/Qwen |
| [04 — Инфраструктура](agent-tasks/04-infrastructure.md) | `infra/**`, root compose/Makefile/env | порты, env и health контракты | повторяемый запуск сервисов |
| [05 — Интеграция и QA](agent-tasks/05-integration-qa.md) | `tests/e2e/**`, `tests/contracts/**`, интеграционные отчеты | все модули | сквозная проверка без переписывания чужих модулей |

Backend — самый крупный пакет. При необходимости его можно разделить **после** создания Laravel-каркаса и утверждения внутренних интерфейсов на `media/batches`, `taxonomy/moderation`, `processing/AI client`, `search`. Один backend-интегратор должен владеть общими маршрутами, регистрацией зависимостей, базовыми моделями и порядком миграций. Без этого четыре backend-агента будут постоянно конфликтовать в одних файлах.

## Правила совместной работы

1. `contracts/**` меняет только владелец контрактов. Любое изменение поведения API сначала оформляется там с примером запроса, ответа и ошибки; затем владельцы реализаций синхронизируют код.
2. У каждого пакета один владелец файлов. Агент может читать чужой модуль, но не редактирует его молча. Нужное изменение передается владельцу как запрос на контракт или отдельный патч.
3. Каждый агент работает в собственной ветке или worktree. Интегратор принимает изменения по одному, запускает проверки контрактов и не сливает несовместимые версии.
4. Контракты фиксируют не только пути, но и авторизацию, поля, обязательность, enum, пагинацию, коды ошибок, idempotency, размеры embeddings и версии моделей. Примеры не заменяют схему.
5. Backend и AI проверяют один и тот же `image-analysis.json`; frontend проверяет публичный API через mock, созданный из OpenAPI. Для CI используются детерминированные фикстуры без GPU.
6. В публичных и AI ответах должен быть `trace_id`/`request_id` по согласованному правилу. Секреты, абсолютные локальные пути и содержимое оригиналов не попадают в коммиты.

## Решения, которые надо закрыть в контрактном этапе

Это не смена требований ТЗ: в этих местах ТЗ задает направление, но не дает достаточно точного контракта для независимой реализации.

| Вопрос | Почему блокирует агенты | Предлагаемое решение для MVP |
| --- | --- | --- |
| Sanctum: cookie-сессия или bearer token; CORS/CSRF | Frontend и backend иначе реализуют login | Зафиксировать один режим, поведение logout и 401/403 в public OpenAPI |
| Формы ответов для списков и деталей; pagination/filter/sort | Нельзя независимо собрать таблицы и API | Единый формат коллекций, поля paging и допустимые фильтры в OpenAPI |
| Dashboard и retry failed image/job | Экраны требуются, но endpoints в §50 не названы | Добавить явные endpoints или закрепить композицию из существующих |
| `POST /api/search`: поле `mode`, пустой query, множественные tag IDs, `debug` | §42 и §45 описывают разные части запроса | Ввести enum `tags/semantic/hybrid`, четкую валидацию и сортировку |
| Batch после duplicate/error, момент `complete`, расчет `total/processed/failed` | UI progress и backend счетчики должны совпадать | Зафиксировать автомат состояний и учет skipped duplicates |
| Кандидат: approve/merge/reject, повторное обнаружение rejected | Иначе модерация создаст циклы и дубли | Зафиксировать атомарность, повторную обработку и судьбу связанных изображений |
| Alias collisions, нормализация Unicode, уникальность тегов по типу | Разные resolver-реализации дадут неоднозначный match | Описать единую нормализацию и правило разрешения коллизий |
| Embedding `model_key`/`model_version`, активная версия, metric/index | Нельзя безопасно смешивать векторы моделей | Искать только внутри одной активной версии; закрепить cosine distance и индекс |
| `/health` против `/ready`; AI error schema и пределы input | Infra, backend и AI должны одинаково понимать готовность | `/health` — жив процесс; `/ready` — модели загружены; формализовать ошибки/лимиты |
| ТЗ показывает массив `embedding` из 2 чисел как сокращенный пример | Схема и тесты ожидают 1152 | В контракте требовать ровно 1152 числа; пример пометить сокращенным или заменить фикстурой |
| Как авторизованно отдаются media-файлы | Нужен согласованный способ для `<img>` в браузере | Описать cookie/token вариант и поведение `X-Accel-Redirect` |

## Готовность к параллельному старту

Пакеты 01–04 получают ссылку на одну версию `contracts/**`; контракты проверены линтером; есть mock ответы на happy path и ошибки; перечисленные решения зафиксированы; владельцы каталогов назначены. После этого агентам не требуется знать внутренности соседних модулей.
