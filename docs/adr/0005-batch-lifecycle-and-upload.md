# ADR-0005: Жизненный цикл batch и параметры upload

- Статус: Accepted
- Дата: 2026-09-25
- Затрагивает: backend, frontend, infra, QA; batches/upload в `public-api.openapi.yaml`, `state-machines.md`

## Контекст

Даны статусы batch (§14), поток create → upload по одному файлу → complete (idempotent) (§26), дубликаты по SHA-256
с ошибкой `IMAGE_ALREADY_EXISTS` (§27), polling progress `{total, processed, failed}` (§49), retry policy
10/30/120 с (§47), «202 / persisted» (§81), max upload size configurable (§63). Не определены переходы, счетчики,
учет дубликатов, HTTP-коды и лимиты.

## Варианты

Счетчики:

- A. `total` = сохраненные изображения; дубликаты не считаются; `processed` = ready + failed; `failed` = failed
  (рекомендуется: прогресс = processed/total доходит до 100% и при ошибках; соответствует колонкам §14).
- B. `processed` = только ready — прогресс «застревает» при ошибках.
- C. Отдельный счетчик `duplicates` — требует новой колонки, которой нет в §14; frontend и так знает дубликаты по 409.

Статус `failed` batch:

- A. Все изображения failed (`failed = total > 0`) (рекомендуется).
- B. Только системная ошибка batch (например, хранилище недоступно) — трудно определить формально.

Retry после финального статуса:

- A. Batch возвращается в `processing`, затем пересчитывается финальный статус (рекомендуется: UI согласован).
- B. Финальный статус «липкий», меняются только счетчики.

Ответ upload:

- A. 201 + ресурс изображения (рекомендуется: ресурс создан синхронно, обработка асинхронна — видно по `status`).
- B. 202 Accepted, как буквально в §81.

## Рекомендация

- Счетчики A, `failed` A, retry A; переходы — `contracts/state-machines.md`.
- Upload: multipart поле `image`; MIME по содержимому — `image/jpeg`, `image/png`, `image/webp`; лимит по умолчанию
  50 MiB (`PHOTO_MAX_UPLOAD_BYTES`), согласованный с `client_max_body_size` nginx и `upload_max_filesize` PHP;
  413 `FILE_TOO_LARGE`, 415 `UNSUPPORTED_MEDIA_TYPE`, 409 `IMAGE_ALREADY_EXISTS` (`details.existing_image_id`),
  409 `BATCH_NOT_ACCEPTING_UPLOADS` после complete.
- Дубликат определяется глобально (unique `images.sha256`, §15), включая soft-deleted изображения — **вопрос**:
  при soft delete unique-индекс продолжает блокировать повторную загрузку того же файла.
- Одновременная загрузка одинаковых файлов: unique-индекс гарантирует один успешный upload, второй получает 409.
- AI retry: `max_attempts = 4` (1 попытка + 3 повтора через 10/30/120 с) — **вопрос**, см. ниже.

## Вопросы

1. Утвердить счетчики A и определение `failed` batch?
2. Допустимые форматы (нужны ли HEIC/TIFF?) и лимит размера по умолчанию?
3. 201 или 202 для upload?
4. §47: 3 попытки всего или 1 + 3 повтора?
5. Разрешать ли повторную загрузку файла, совпадающего с soft-deleted изображением (восстановление или 409)?
6. Нужно ли автозавершение batch, для которого не вызван complete (например, через N часов)?

## Принятое решение

Владелец продукта утвердил этот пункт 2026-09-25. Итоговая формулировка: batch/upload.** `total` считает сохранённые изображения без дублей; `processed = ready + failed`; batch `failed`, когда все сохранённые изображения failed. Retry возвращает batch в processing. Форматы JPEG/PNG/WebP, лимит загрузки 50 MiB, поле `image`, ответ 201. AI получает уменьшенную копию в пределах своего лимита 20 MiB; оригинал остаётся неизменным. Политика AI: первая попытка + 3 повтора через 10/30/120 секунд. Совпадение SHA-256 с soft-deleted изображением возвращает 409; автоматического закрытия batch без вызова complete нет.
