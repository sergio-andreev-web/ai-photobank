# ADR-0007: Нормализация тегов и aliases, коллизии, archive/delete

- Статус: Accepted
- Дата: 2026-09-25
- Затрагивает: backend (TagResolver, taxonomy API), frontend (формы тегов), QA

## Контекст

Нормализация: trim, lowercase, unicode normalize, normalize whitespace (§35). Unique `tags.normalized_name + type`
(§16), aliases с `normalized_alias` без unique (§17), resolver: stage 1 exact canonical, stage 2 alias, stage 3
semantic (§36). Delete — archive, если тег используется (§50). Не определены форма Unicode, коллизии между тегами
разных типов и aliases, поведение с архивными тегами.

## Рекомендация по нормализации (одна функция в backend, покрытая тестами)

1. Unicode NFKC.
2. Lowercase по Unicode (`mb_strtolower`).
3. Все пробельные символы (включая NBSP) → пробел; схлопнуть повторы; trim.
4. `ё` не заменяется на `е`; пунктуация и дефисы не удаляются (изменение — только решением координатора).

## Коллизии — варианты

- A. Глобальная уникальность «имени»: `normalized_alias` уникален глобально и не совпадает с `normalized_name`
  любого другого тега; `normalized_name` нового тега не совпадает с чужим alias (рекомендуется). Stage 2 всегда дает
  не более одного тега.
- B. Уникальность в пределах типа, stage 1/2 учитывают `concept.type`. Требует доверять типу от VLM, который может
  ошибаться (object vs concept), — одинаковые понятия разойдутся по разным тегам.
- C. Без ограничений, при нескольких совпадениях — кандидат для модерации.

Коллизия `normalized_name` у тегов разных типов остается допустимой по §16 (например, «ключ» object и «ключ» concept).
Для stage 1 при нескольких совпадениях предлагается: сначала тег с тем же `type`, что у concept; если такого нет и
совпадений больше одного — ничего не назначать и создать/обновить кандидата с `closest_tag_id` лучшего по embedding.

## Рекомендация

- Коллизии A → 409 `TAG_ALREADY_EXISTS` / `ALIAS_ALREADY_EXISTS` с `details.existing_tag_id`.
- `DELETE /tags/{id}`: «используется» = есть image_tags, дочерние теги или ссылка `tag_candidates.closest_tag_id`
  → archive, 200; иначе физическое удаление, 204.
- `PATCH status`: archive/restore. Архивный тег: связи сохраняются; новые назначения запрещены (409 `TAG_ARCHIVED`);
  resolver при совпадении с архивным тегом concept игнорирует (без кандидата).
- `parent_id`: не сам тег, не потомок, не архивный → иначе 422 `TAG_PARENT_INVALID`. Тип родителя не ограничивается.
- `slug` генерирует backend (транслитерация + суффикс при коллизии); в запросах не передается.
- Любое изменение name/alias регенерирует tag embedding (§21) асинхронно.
- Alias в URL удаления — числовой ID alias.

## Вопросы

1. Утвердить вариант A для коллизий?
2. Правило stage 1 при совпадении имени у тегов разных типов?
3. Что делать при совпадении concept с архивным тегом — игнорировать или создавать кандидата?

## Принятое решение

Владелец продукта утвердил этот пункт 2026-09-25. Итоговая формулировка: теги и aliases.** Нормализация NFKC + Unicode lowercase + схлопывание пробелов, `ё` сохраняется. Alias уникален глобально и не пересекается с canonical name другого тега. Одинаковые canonical names разных типов допустимы; при выборе сначала учитывается тип concept, при неоднозначности создаётся кандидат. Совпадение с архивным тегом не создаёт нового назначения или кандидата.
