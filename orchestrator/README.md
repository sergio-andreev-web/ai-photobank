# Оркестратор агентов для AI Photobank

Это небольшой локальный диспетчер, а не отдельный LLM и не прокси для пользовательского приложения. Он принимает описанные задачи, выбирает CLI и модель по [`policy.json`](policy.json), строит prompt с нужным заданием и запускает исполнителя в отдельном Git worktree. Выполненная работа требует ручного review и merge. Задачи в [`tasks.json`](tasks.json) разделены на отдельно принимаемые срезы с явными зависимостями.

## Почему правила, а не «AI-начальник»

Модель назначается по сложности конкретного среза. Например, простые миграции `backend-schema-base` получает GPT-6 Luna, схемы с pgvector `backend-schema-domain` — Claude Sonnet 5, а доменные правила `backend-processing`, `backend-taxonomy` и `backend-search` — Claude Opus 5.5 по умолчанию. При выборе Codex для них используется GPT-6 Sol. Полная таблица находится в [`docs/model-routing.md`](../docs/model-routing.md).

## Подготовка

Нужны Python 3, Git и установленный `codex`/`claude` CLI с рабочей авторизацией. Для параллельного запуска нужен Git-репозиторий с чистым текущим checkout и хотя бы одним коммитом. Оркестратор не создает аккаунты, ключи и не запускает агентов сам по расписанию.

```bash
python3 scripts/orchestrate.py doctor
python3 scripts/orchestrate.py usage
python3 scripts/orchestrate.py list
python3 scripts/orchestrate.py plan contracts-v1
python3 scripts/orchestrate.py plan backend-processing --provider codex --model gpt-6-sol
```

`plan` не запускает агента и показывает фактически выбранную модель, проценты подписок, причину выбора и блокирующие зависимости. `list` показывает модели из политики без проверки текущих подписок; для актуального решения по одной задаче используйте `plan TASK`. Пока `contracts-v1` не принят, зависимые задачи помечаются как blocked. После него отдельно принимаются контрактные примеры `contract-fixtures`, затем могут параллельно стартовать первые задачи backend, frontend, AI и инфраструктуры.

`usage` читает Codex через локальный CLI app-server `account/rateLimits/read`, Claude — через локальную команду `claude -p '/usage'`. **Для маршрутизации сравниваются пятчасовые остатки** (`primary` и `Current session`); недельные лимиты служат отдельной проверкой доступности. Источники не используют API-баланс или токены из логов вместо лимита подписки. При недоступности одного источника автоматический выбор использует другой и сообщает об ошибке; если оба недоступны, запуск блокируется. Если разница пятчасовых остатков меньше 10 процентных пунктов, сохраняется предпочтительный провайдер задачи. Порог и разница настраиваются в `policy.json`.

## Запуск и приемка

```bash
python3 scripts/orchestrate.py run contracts-v1
python3 scripts/orchestrate.py run backend-processing --provider claude --model claude-opus-5-5
python3 scripts/orchestrate.py run backend-processing --provider codex --model gpt-6-sol
python3 scripts/orchestrate.py status
python3 scripts/orchestrate.py logs contracts-v1 --follow
```

`run` без флагов проверяет оба остатка и запускает процесс в фоне на выбранном провайдере. `--provider` выбирает Codex или Claude вручную; `--model` выбирает точную модель из `allowed_models` в политике и может использоваться без `--provider`. Модели Codex ограничены GPT-6 Luna и Sol. Явный выбор тоже проверяет остаток выбранной подписки; при сбое проверки можно сознательно добавить `--skip-usage-check` вместе с явным выбором. `run` возвращает `run_id`, модель, причину выбора, снимок лимитов, ветку и worktree. Следующие независимые задачи можно запускать так же; два задания с одной зоной владения одновременно не стартуют. `status` показывает стадию (`queued`, `running`, `needs_review`, `failed`, `scope_violation`, `accepted`), модель, ветку, worktree и путь лога. `logs TASK --follow` показывает действия агента по мере выполнения; `--raw` выводит полные JSONL события. Можно передать `run_id` вместо имени задачи. Диспетчер записывает prompt, лог и состояние в `.orchestrator/runs/<run_id>/` — эта папка игнорируется Git и может содержать чувствительную информацию.

## Контрольная точка и продолжение

Пока агент работает, диспетчер каждые 30 секунд проверяет остаток подписки активного провайдера. При остатке пятчасового окна 25% или меньше, недельного окна 10% или меньше, а для Fable также его отдельного недельного окна 10% или меньше, он просит агента завершить текущую безопасную правку и сообщить, что сделано и что осталось. Пороги и интервал задаются в `policy.json` (`usage_monitor`). Можно запросить это вручную:

```bash
python3 scripts/orchestrate.py checkpoint contracts-v1
python3 scripts/orchestrate.py status
python3 scripts/orchestrate.py logs contracts-v1 --follow
```

Статус `checkpointing` означает, что запрос передан; `checkpointed` означает, что остановка завершена. После этого прочитайте `.orchestrator/tasks/<task_id>/checkpoint.md` и `checkpoint.json`. Там сохраняются отчет агента, измененные файлы, причина остановки, снимок лимита, исходная ветка/worktree и ID родной сессии; полный ход работы остается в `.orchestrator/runs/<run_id>/agent.log`. Изменения кода остаются в том же worktree. При следующем запуске можно выбрать провайдера и модель заново:

```bash
python3 scripts/orchestrate.py resume contracts-v1
python3 scripts/orchestrate.py resume contracts-v1 --provider claude --model claude-sonnet-5
python3 scripts/orchestrate.py resume contracts-v1 --provider codex --model gpt-6-sol
```

`resume` сначала снова проверяет подписки, затем продолжает в прежнем worktree. При том же провайдере диспетчер передает CLI ID прежней сессии, если он известен. При смене Codex ↔ Claude новый агент получает сохраненную контрольную точку и проверяет незавершенный diff. Внутренний контекст чужой модели не переносится; отчет и файлы служат передаваемым контекстом. Старые логи остаются доступны по `run_id`; новый прогон получает собственный лог. Задача со статусом `checkpointed` удерживает свою зону владения и блокирует пересекающиеся задачи до завершения и приемки.

Запрос на остановку выполняется по возможности: при резком исчерпании лимита агент может не успеть написать отчет. Если статус `checkpointed`, диспетчер всё равно сохраняет путь к worktree, измененные файлы и лог в контрольной точке. Если процесс уже завершился со статусом `failed`, команда `resume` создаст контрольную точку из сохраненного diff и лога и продолжит в том же worktree. Перед продолжением просмотрите эти артефакты. При `scope_violation` сначала разберите изменения вне зоны владения.

## Приемка

После `needs_review` человек смотрит diff в worktree, проверяет тесты и соответствие контракту, затем коммитит изменения в ветке агента и сливает ее в основной checkout. Только после этого:

```bash
python3 scripts/orchestrate.py accept contracts-v1
```

`accept` проверяет, что ветка действительно вошла в текущий HEAD. Он не делает merge и push автоматически. После приемки разблокируются следующие задачи. Статус `scope_violation` означает, что агент изменил файл вне своего пакета: изменения остаются в изолированном worktree для разбора, а следующий запуск в пересекающейся зоне блокируется.

Если процесс завершился ошибкой, задача получает `failed`; после диагностики ее можно продолжить через `resume` в прежнем worktree либо запустить заново через `run`. Старый worktree и лог остаются для анализа. Не удаляйте их, пока не разобрали результат.

## Провайдеры

- **Codex:** `codex exec` с выбранной моделью, workspace-write sandbox и JSONL логом.
- **Claude:** `claude --print --output-format stream-json` с выбранной моделью, без интерактивных approval prompts; команды, требующие подтверждения, могут быть отклонены и должны попасть в отчет агента.
- **Ollama:** выключен по умолчанию. После проверки локальной coding-модели укажите ее ID и `enabled: true` в `policy.json`; запуск идет через Codex CLI `--oss --local-provider ollama`. Ollama разрешен только для перечисленных узких `allowed_kinds`.

Маршрутизация задается в `policy.json`, а объяснение выбора моделей — в [`docs/model-routing.md`](../docs/model-routing.md). Если модель недоступна в вашем аккаунте, диспетчер не подменяет ее молча: используйте другой провайдер или измените политику осознанно. Источники процентов — локальные команды текущих авторизованных аккаунтов; если формат их ответа изменится, проверка остановится с явной ошибкой.

## Добавление задачи

Добавьте объект в `tasks.json` с уникальным `id`, `title`, `module`, `kind`, `depends_on` и конкретными `instructions`. `module` определяет файлы, которыми можно владеть; `kind` — маршрут модели. Необязательное `preferred_provider` выбирает провайдера для конкретной задачи, если тот разрешен маршрутом. Зависимости могут указывать на задачи, которые будут приняты позже: оркестратор блокирует запуск до их приемки. При работе над новым API сначала добавьте зависимость от контрактной задачи.

Оркестратор проверяет зоны владения **после** работы агента и изолирует изменения worktree. Это полезный контроль конфликтов, но не абсолютная песочница для всех файлов на машине. Не передавайте недоверенному агенту секреты или избыточные права.
